Loom：一个把大模型当作外设，
而不是内核的操作系统

绝大多数「AI 操作系统」在第一步就走错了：它们试图让大模型去做内核该做的事。这份文档提出相反的结构——让确定性内核持有全部执行权，让模型只负责理解与提议，并用一条可审计的窄腰把两者隔开。

01三条路线与各自天花板

把大模型装进操作系统，目前能看到三条路，每条都有人在走，每条都撞到了不同的墙。

路线 A：把 LLM 当内核

代表是 AIOS 这一类研究：LLM 视为 CPU、上下文窗口视为内存、工具调用视为系统调用，在应用与模型之间插一层「AIOS 内核」，负责调度、上下文切换、内存管理、访问控制。工程价值是真实的——论文报告并发场景下有约 2.1 倍加速，因为把上下文管理和调度从各个 agent 框架里抽出来了。

但那个类比会误导架构。CPU 是确定性的、可抢占的、状态可以被完整保存和恢复的；LLM 每一条都不成立：它输出不可复现，上下文即状态，一次推理中途换出等于重算整个 KV。把 LLM 当 CPU，就会自然推导出「LLM 上下文切换」这种代价极高、且本不该存在的机制。

更准确的位置是：LLM 是一块高延迟、有损、需要大量随附状态的协处理器。操作系统的任务不是让它当大脑，而是虚拟化它——向上提供确定性服务，向下吸收不确定性。

路线 B：把助手塞进系统

Copilot+ PC、各类系统级 Agent 入口都属于这一类。它的问题是天花板被交互模型锁死：用户仍然在「开应用—找文件—点按钮」，AI 只是某个环节的加速器。系统的资源抽象、权限模型、状态单位一个都没变，所以它永远只能是插件，不可能成为操作系统。

路线 C：把权限收进内核

这条是 2025 年之后最有价值的一步。微软的 ACS / MXC 把 Agent 行为切成 8 个拦截点（agent_startup、input、pre_model_call、post_model_call、pre_tool_call、post_tool_call、output、agent_shutdown），用 OPA/Rego 声明式策略做 allow / warn / deny / escalate 四档裁决，再用可组合沙箱做强制隔离，并且给 Agent 分配独立身份——它删了文件，日志里记的是 Agent，不是人。

这条路的判断是对的：Agent 安全的未来在内核，不在提示词里。但它只解决了一半——它管住了「谁能做什么」，没管住「模型看到的东西可不可信」。而后者才是 AI 系统独有的、传统 OS 从未面对过的攻击面。

结论

三条路线各对了一部分：A 对了「需要一层 AI 运行时」，B 对了「交互必须重做」，C 对了「执行权必须下沉到内核」。真正缺的那块拼图是：信任必须成为数据的属性，并随数据在系统内流动。这决定了整个架构的形状。

02第一性原理：操作系统管的是稀缺资源

回头看操作系统的历史，每一次演进都是因为出现了一种新的稀缺资源，然后系统围绕它重建抽象。

时代新出现的稀缺资源操作系统给出的回答
1960s 批处理CPU 时间进程、时间片轮转
1970s 分时内存虚拟地址空间、页表、MMU
1980s 个人计算磁盘与文件文件系统、目录树
1990s 网络连接与事件socket、select/epoll
2000s 移动电量与触摸电源管理、生命周期、手势模型
2020s 之后四样同时变稀缺还没有答案

这一次不是一种资源变稀缺，是四种同时变稀缺，而且互相冲突：

R1

推理算力

NPU 的 TOPS 有限，而且被功耗和散热卡死。它不是可以无限加核的 CPU。

R2

上下文窗口

新的「内存」，但它是会遗忘的内存：容量有限、访问有损、写错了还会一直错下去。

R3

可信上下文

真正稀缺的不是信息，是能证明来源可信的信息。混进一段网页文本，整个决策链就被污染。

R4

人的注意力

Agent 越多，请求确认的次数越多。人成了系统里吞吐最低、最容易饱和的那个组件。

R4 值得多说一句。传统操作系统从来没有把「什么时候可以打断人」当成一个需要调度的资源——中断是硬件来的，数量可控。但 AI 系统里，每一个后台 agent 都「有话要说」，都想请求确认、汇报进度、报告异常。如果不加调度，用户会在半小时内被淹没，然后学会全部点「同意」，安全机制就此失效。把注意力当资源来调度，是这个系统里最反直觉、也最不可省略的一块。

03六条设计公理

Ⅰ

AI 提议，内核执行

大模型永远不进入可信计算基（TCB）。它可以读、可以想、可以说，但任何改变外部世界的动作，必须由内核在能力校验之后代为执行。这条公理一旦松动，后面所有安全设计都会失效。

Ⅱ

信任是数据的属性，不是进程的属性

传统 OS 的信任边界画在进程上：这个进程可信，那个不可信。但一个 agent 进程里，既有用户亲口说的指令，也有刚从网页抓来的段落。两者必须被区别对待，而且这个标签要随数据流动——这就是污点追踪在 AI 时代的复活。

Ⅲ

一切副作用必须可补偿

传统 OS 用隔离防止一个进程破坏另一个；但 agent 会真实地改变世界：发邮件、下单、删文件、转账。隔离挡不住已经发出去的邮件。所以撤销不是产品功能，是安全机制，必须和权限检查同级。

Ⅳ

确定性外壳，概率性内核

理解、规划、生成这些环节尽量往上推，允许不确定；鉴权、执行、记录、回滚尽量往下压，必须确定。系统的形状是一个窄腰沙漏，不是一根直筒。

Ⅴ

降级是一等公民

模型不可用、断网、超出预算、电量告急时，系统必须能退回传统交互并保持可用。这条约束看起来是妥协，实际上是最好的架构检验器：如果系统离了模型就开不了机，说明分层是假的。

Ⅵ

可重放才能运维

每一个决策点、每一次工具返回都必须可记录、可复现。没有这个，AI 系统在出问题的时候无法定位——你不能对一个概率系统说「你再跑一遍我看看」。

04总体架构

为什么不把 AI 运行时放进内核

诱惑很大：上下文管理、推理调度看起来和内存管理、CPU 调度很像，放内核里「效率更高」。但代价不可接受：内核会因此依赖一个每次更新都会变的外部组件，可信计算基从几万行涨到几百万行（还包含模型权重），形式化验证彻底失去可能，一个提示注入就可能直达最高权限。

正确做法是：AI 运行时是一个特权但不被信任的用户态服务集。它通过正常的能力申请流程去请求内核做事，和任何第三方 agent 待遇一样，只是它的能力集合更宽、优先级更高。这样即使它被完全攻破，攻击者拿到的也只是它当时持有的那几张能力令牌。

一个可检验的判据

如果明天把所有模型文件删掉，系统还能开机、还能打开文件、还能用传统方式完成大部分日常操作——架构是对的。如果开不了机，那它就不是操作系统，是一个包装成操作系统的应用。

05新的内核对象

操作系统之所以是操作系统，在于它定义了一套别人绕不过去的抽象。Loom 在传统的进程/线程/文件/描述符之外，引入五个新对象。

对象是什么传统对应物关键属性
Intent 意图一个带约束、预算、成功判据的目标命令行参数 / 作业可澄清、可放弃、有截止时间
Agent 代理为达成意图而存在的执行体进程有独立地址空间、独立身份、能力集合
Capability 能力不可伪造、可衰减、可委托、会过期的凭证文件描述符精确到「哪个对象、什么操作、多久、几次」
Context Handle 上下文句柄一段带信任标签的上下文视图内存映射可撤销、带污点、可被引用计数
Effect 效果一次对外部世界的改变，事务化系统调用幂等键、补偿动作、可重放

系统调用表

抽象最终要落成接口。下面是这套设计的原语集合——数量刻意保持在个位数，因为每多一个原语，安全审计的复杂度就翻一倍。

原语签名对应语义

绑定上下文ctx_attach(task, handle, trust)mmap把带信任级别的上下文映射进任务

执行动作act(cap, args) → txnwrite / ioctl唯一能改变外部世界的入口，返回事务
提交 / 回滚txn_commit(txn) / txn_abort(txn)fsync事务化，失败自动走补偿

注意 mem_recall 返回的是 items + conf 而不是单纯的 items。这个细节很关键：检索是概率的，系统必须知道「我可能没找到」。置信度低于阈值时，正确的行为不是硬着头皮往下走，而是升级成一次 yield，问用户一句。这条规则能消掉相当比例的错误执行。

06五个调度器

这是整套设计里最核心的一块。传统 OS 有两个调度器（CPU、内存），加一个 IO 调度；Loom 需要五个，其中三个是新的。

调度器调度对象优化目标策略要点
① 算力调度器线程、页、IO 队列利用率与尾延迟沿用成熟做法，为推理任务预留实时通道
② 推理调度器 新token、KV cache、NPU 时间片首 token 延迟、吞吐、每焦耳 token 数分级 SLA、前缀缓存复用、可抢占批处理
③ 上下文调度器 新上下文窗口（会遗忘的内存）有效信息密度、语义缺页率语义换页、摘要驱逐、按需重取
④ 注意力调度器 新人的打断次数与时机「这次打断值得」的比例合并、延迟、批量、静默期、重要度分级
⑤ 信任调度器 新能力令牌越权成功率、爆炸半径最小权限、短租约、逐级升级、可撤销

② 推理调度器：把 KV cache 当页缓存

这里有一个被低估的优化空间。多个 agent 往往共享大量相同前缀（同一份系统提示、同一份文档、同一段对话历史）。传统做法是每个 agent 各算一遍。Loom 把 KV cache 当作可跨 agent 共享的页缓存：相同前缀只算一次，命中即复用，并按 LRU 淘汰。

再叠加分级 SLA：交互式请求（用户正在等）走实时通道，抢占后台批处理；后台任务（夜间整理、索引重建）只在设备充电、空闲、温度安全时运行。这两条加起来，端侧体验可以从「等三秒」变成「几乎即时」。

③ 上下文调度器：语义缺页

上下文窗口是新的内存，但和真内存有一个本质区别：缺页是概率的。真 MMU 的缺页是确定的——地址不在页表里，就去磁盘取，一定取得到。语义缺页是概率的——「我记得有个德国供应商的合同」，检索可能返回错的，也可能什么都返回不了。

所以上下文调度器必须维护一个显式的「缺页置信度」，并定义三级降级：置信度高 → 直接用；中等 → 补充检索或换一种表述再试；低 → 停下来问人。把「我不知道」变成一个可调度的事件，而不是让模型编一个答案。

④ 注意力调度器：中断合并

这是最容易被忽略、但用户感受最强烈的一个。设计上借用网络里的中断合并（interrupt coalescing）思路：

  • 合并：同一意图下的多个确认请求打包成一次交互，而不是逐个弹窗。
  • 延迟：非紧急请求进入队列，等到用户自然停顿点（切换任务、锁屏前）再呈现。
  • 分级：只有不可逆且高风险的动作（转账、对外发送、删除）才允许立即打断；其余一律排队。
  • 静默期：用户刚拒绝过一次，同类请求在接下来一段时间内不再询问，改为默认拒绝。

目标是让「误中断率」——用户认为这次打断不值得的比例——控制在 5% 以下。这个指标听起来软，但它直接决定了安全机制会不会被用户习惯性绕过。

⑤ 信任调度器：把安全当调度问题

换个视角看权限：它不是一道静态的门，而是一种随时间逐步发放、可随时收回的资源。一个 agent 开始只拿到「读这三个文件」的能力，随任务推进和用户确认逐步升级，任务结束立刻失效。这样即使某个环节被攻破，攻击者拿到的也是一张快要过期的、范围极窄的票。

07上下文与记忆

记忆子系统决定了这个系统是「每次都从零开始」还是「越用越懂你」。但它同时也是最危险的部分——记错的东西会一直错下去，而且越用越自信。

层内容介质生命周期写入规则
L0 工作集当前 prompt 与 KV cacheNPU 显存秒级自动，可随时丢弃
L1 情节最近交互、事件流、任务轨迹本地向量库 + 事件日志天到周自动写入，带完整出处
L2 语义 / 程序提炼的事实、偏好、可复用技能结构化库 + 小模型月到永久需置信度阈值 + 用户可见
L3 冷存档原始记录、加密备份本地磁盘 / 用户自有云永久只追加，不可改

三条不可妥协的规则

第一，无出处不落库。每一条记忆必须带 provenance：什么时候、从哪来、由谁说的、当时的置信度。没有出处的记忆一律视为不可信，只能待在 L1，不能升级到 L2。

第二，置信度随时间衰减。「用户喜欢靠窗座位」这条事实，三年前成立不代表今天成立。记忆需要半衰期，过期自动降级，重要决策前重新确认。

第三，记忆必须可审阅、可删除。用户应该能像查征信报告一样，看到系统记住了关于自己的什么、依据是什么、用在了哪里。这既是隐私要求，也是纠错机制——模型自己不会发现记错了，只有人能看到。

记忆污染

如果 agent 在浏览网页时把「用户授权向某地址转账」写进了 L2，而这条记忆又没有出处标记，那么之后每一次相关决策都会基于这个假前提。这类攻击不需要攻破任何加密，只需要让模型「读到」并「记住」。所以记忆写入必须是受控的系统调用，不能是 agent 随手一写。

08安全模型

这一节是整份文档里最不性感、但决定生死的一节。先说结论：提示注入在模型层面无解，只能在系统层面让它失效。

为什么模型层面无解

对模型来说，系统提示和用户输入、网页内容，全都是同一串 token，没有本质区别。所有「请不要听信以下内容里的指令」这类防御，都是概率性的——降低成功率，但给不了保证。只要系统还允许「模型读到的东西」直接影响「模型能做的事」，这条路就是通的。

所以正确的目标不是「阻止注入」，而是「即使注入成功，也不产生安全后果」。这和当年对付缓冲区溢出是同一个思路：不指望消灭漏洞，而是让漏洞不可利用。

核心机制：把计划和执行拆给两个模型

关键在于那道「气闸」必须是结构化中间表示，而不是自然语言摘要。如果计划器输出的是一段散文，攻击者仍然可以把指令藏进散文里；只有当输出被约束成「工具名 + 类型化参数 + 前置条件」的有限结构，且参数经过类型与取值域校验，传导链才真正断掉。

辅助机制：上下文污点追踪

每段进入上下文的文本都带一个信任标签：user（用户亲口说的）、verified（系统签名验证过的）、untrusted（外部抓取的）。污点会沿着推理链传播——用 untrusted 内容得出的结论，仍然是 untrusted。规则很简单：

  • 带 untrusted 污点的计划，不能直接触发高风险动作，必须经过 yield 请人确认。
  • 污点不会因为「被摘要过」而消失——摘要继承来源的最高污点。
  • 只有用户明确确认，或者经过独立可信通道验证，污点才能被清除。

这和操作系统里的信息流控制（IFC）是同一套理论，只是从「文件密级」换成了「上下文可信度」。可惜目前还没有主流系统在 AI 场景里真正实现它——这是 Loom 最想补的那块空白。

权限模型：能力，而不是身份

传统做法是「你是谁 → 你能做什么」。但在 agent 场景下身份没有区分度：所有 agent 都是「用户的代理」，按身份授权等于给了它全部权限。所以必须换成能力模型：

  • 不可伪造：能力令牌由内核签发，用户态无法构造。
  • 可衰减：可以把自己的能力缩小后转授（只读、单文件、十分钟），但不能放大。
  • 短租约：默认 10 分钟过期，长期任务需周期性续租，续租时重新评估风险。
  • 可撤销：任何时刻一键收回，正在进行的动作立即中止并触发补偿。
  • 可归因：每次使用都记录在行动账本上，能回答「这个文件是谁在什么时候为什么读的」。

09动作与事务：让撤销成为原语

隔离挡不住已经发出去的邮件。这是 AI 系统和传统系统的根本差异：它的错误会离开计算机。

所以每一个 act() 都必须在一个事务里执行，并附带三类元数据：

  • 幂等键：重试不会重复下单。这在网络不稳定、agent 反复重试时是救命的。
  • 补偿动作：如果后续步骤失败，怎么撤回这一步。发邮件没有真正的补偿，那就必须在发送前设更高的确认门槛——不可补偿的动作，必须用更严的前置约束来换。
  • 前置条件：执行前世界必须处于什么状态。条件不满足则整个事务不启动，而不是做到一半才发现。

这套东西在分布式系统里叫 Saga，很成熟，但从来没有被搬进个人操作系统。搬进来之后，用户获得的能力是：「刚才那三步，撤回」——而且系统知道该按什么顺序、调用哪些反向操作去撤。

诚实的边界

不是所有动作都可补偿。钱转出去了、消息已读、硬盘上的文件被外部程序覆盖——这些只能做到「尽快发现 + 尽力挽回 + 明确告知」。设计上必须把动作分成三档：可完全补偿（本地文件操作）、可部分补偿（撤销 API 存在但有时间窗）、不可补偿（对外通信、支付、物理动作）。第三档必须走最严格的确认路径，且不允许后台 agent 自主执行。

可重放：给概率系统装一个调试器

传统系统出问题，复现一遍就行。AI 系统不行——同样的输入，模型可能给出不同结果。所以 Loom 在系统层记录一份「决策轨迹」：每个决策点的输入摘要、模型版本与参数、输出、工具返回、当时的能力集合。有了它，才能做时间旅行调试：回到第 7 步，看当时模型看到了什么、为什么选了那个工具。

这份轨迹同时也是合规审计、责任归属、以及模型迭代时回归测试的基础设施。没有它，这个系统在真实环境里无法运维。

10交互层：从「开应用」到「说意图」

意图栏取代启动器

主入口不再是图标网格，而是一个输入框——但它的语义和搜索框完全不同：搜索框返回链接，意图栏返回已完成的结果或正在进行的任务。「把上个月的发票整理成报销单」应该直接产出一个填好的表单，而不是十个可能相关的文件。

关键设计是渐进披露：第一屏只给结论和最关键的一个操作；想深究时展开证据（依据了哪些文件、哪几条记忆）；再深一层是完整的执行轨迹。绝大多数时候用户停在第一层，但必须随时能下钻——这是信任的来源。

生成式界面必须被约束

让模型直接生成 UI 很诱人，但会带来三个问题：不可测试、不可无障碍访问、不可审计。Loom 的做法是约束解码到组件词汇表：系统提供一套经过设计、测试、带无障碍标注的组件，模型只能输出「用哪些组件、什么内容、什么布局」的声明式描述，由系统渲染。

这样既保留了「界面随任务而变」的灵活性，又保证每个像素都来自可信代码。用一句话概括：模型决定说什么，系统决定怎么画。

环境感知要有可见的开关

系统需要知道用户当前在做什么，才能做出合理判断。但常驻感知是最容易引发反感的能力。三条约束：默认全部在端侧处理，原始数据不出设备；任何时候都有物理可见的指示（不是藏在设置里的小圆点）；一键可关，且关闭后系统明确降级而不是偷偷继续。

11兼容与生态：不要要求别人重写

历史上所有新操作系统的死因几乎相同：没有应用。要求开发者为新平台重写一遍，是最慢的路。

Loom 的答案是反向适配：不去要求应用支持 AI，而是让系统去驱动已有应用。

  • 自动化桥接：通过无障碍树、UI 自动化接口、脚本接口，把已有应用的界面元素暴露成系统工具。老应用不需要改一行代码，就获得了被 agent 调用的能力。
  • 渐进升级：应用可以选择只提供「语义化动作」（推荐），系统就不必去猜界面；不提供也能用，只是可靠性低一些。
  • 工具即驱动：把「一个应用能做什么」定义成和设备驱动类似的声明式清单，系统统一编排、统一鉴权、统一记账。

这条路不优雅，可靠性也不如原生集成，但它是唯一能在第一天就有生态的路。先用桥接活下来，再让原生集成变成性能优势，而不是准入条件。

12七个硬问题

下面这些是设计里没有真正解决的问题。列出来，是因为一份只讲优点的架构文档没有价值。

1. 间接提示注入——根本上未解

双模型分离能切断「读到的内容 → 直接执行」的路径，但切不断「读到的内容 → 影响计划 → 计划本身是合理的但目标被扭曲」。比如攻击者不要求转账，只是让 agent「顺便把这封邮件转发给财务」，这看起来完全合理。这类语义层的操纵目前只能靠概率性检测和人工确认，没有确定性方案。这是整个领域未来三到五年最重要的开放问题。

2. 长任务会「卡住」而不报错

agent 跑二十分钟后开始重复同一个失败动作，或者陷入两个工具之间的循环。系统需要检测这种「无进展」状态并主动中止——类似于看门狗定时器，但判据是语义的（任务状态有没有实质推进），比硬件看门狗难得多。

3. 级联路由的准确率上限

用小模型处理大部分请求、难的交給大模型，是控制成本和延迟的唯一现实方案。但「难不难」的判断本身要靠一个分类器，它会犯错：简单问题被误判为难的，只是慢一点；难问题被误判为简单的，就是错误执行。这个误判率决定了整个体验的下限。

4. 评估体系缺失

现在没有公认的「操作系统级」benchmark。MMLU 之类的分数和「能不能帮用户把报销单填对」几乎没有相关性。需要的是任务完成率、澄清恰当率、撤销率这类系统指标——而这需要真实的长周期用户数据，不是刷榜能解决的。

5. 常驻感知的功耗

「随时待命」和「一天一充」是直接冲突的。可行的方向是事件驱动而非轮询：绝大多数时间 NPU 处于休眠，由廉价传感器或规则引擎触发唤醒，只在真正需要理解时才调用模型。但这要求系统对「什么事件值得唤醒」有很好的判断，又是一个准确率问题。

6. 用户的信任校准

用户会走向两个极端：过度信任（不看就点同意）或过度怀疑（每次都拒绝，系统形同虚设）。好的设计应该让确认请求少而准——宁可少问但每次都问在关键处，也不要频繁打扰导致习惯性同意。这更像产品设计问题，但它决定了安全机制的实际有效性。

7. 生态与标准的博弈

如果每家公司都定义自己的「工具描述格式」和「能力模型」，最后会变成一堆互不兼容的孤岛。这一层需要标准化，但标准化通常发生在市场格局确定之后，而不是之前——这是个先有鸡还是先有蛋的问题。

13度量体系

没有度量就没有工程。Loom 用下面这组指标判断自己是否真的做对了，而不是看模型跑分。

14落地路线

从零写一个内核是十年、数十亿美元量级的工程。任何声称三年做出新内核的计划都不值得认真对待。现实的路径是三段式，每段都能独立交付价值。

阶段时间做什么不做什么验证什么
P0 外壳0–12 月在 Linux / Android 之上做意图栏、语义索引、效果总线、能力模型不碰内核，不做多任务并发交互模型是否成立：用户是否真的愿意「说意图」而不是「开应用」
P1 系统服务12–30 月替换系统服务层：推理调度器、上下文管理器、记忆、行动账本、双模型分离不动内核，沿用现有驱动生态安全模型是否可强制：注入攻击能否被结构性阻断
P2 内核30–60 月自研微内核（seL4 风格 + Rust 实现），能力原生、形式化验证关键路径不追求全功能，只做能力与隔离可信计算基能否压到可验证的规模

MVP：一个垂直切片，而不是一个平台

第一版不要做「通用助手」，要做一条端到端的窄流程：邮件 + 日历 + 本地文件。用户说「下周去上海出差，帮我把行程排一下」，系统需要完整走通：理解意图 → 检索历史偏好（记忆）→ 读日历找空档（能力申请）→ 查航班（网络工具）→ 生成行程（生成式界面）→ 用户确认 → 写日历（事务）→ 可撤销。

这条流程覆盖了所有核心机制：意图、记忆、能力、事务、生成式 UI、撤销、双模型分离。它跑通了，架构就成立；跑不通，问题会立刻暴露在最贵的地方之前。

15战略定位：别在 PC 和手机上正面开战

最后一个判断，可能比前面所有技术设计都重要。

PC 和手机上有 Windows、Android、iOS，它们有二十年积累的应用生态、驱动生态、开发者习惯。AI 原生 OS 在这两个战场上没有胜算——不是因为技术不行，是因为迁移成本由用户承担，而收益是渐进的。

真正的机会在没有存量生态的新形态设备：

  • 具身智能 / 机器人：交互天然是「说目标」，不是「点按钮」。没有历史应用要兼容，感知—决策—执行的闭环本来就是 OS 该管的事。
  • 智能座舱：驾驶场景下用户不能看屏幕、不能点按，意图式交互是唯一合理的选择，而不是可选项。
  • AI 眼镜 / 可穿戴：屏幕极小，UI 必须由系统按需生成，固定界面范式根本不成立。
  • 工业与专用终端：任务高度结构化，可靠性要求高，正好是「可审计 + 可回滚」价值最大的地方。

这些场景有一个共同点：它们不需要说服用户放弃现有习惯，因为它们本来就是新的。在这里把架构跑通、把可靠性磨出来，再回头打通用计算，胜率会完全不同。

一句话总结

这个操作系统的竞争力不在于「模型有多聪明」——那是别人的战场。它在于：当模型犯错、被欺骗、或者干脆不可用时，系统还能保证什么。这才是操作系统这个词真正承诺的东西。
