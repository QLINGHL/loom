01三条路线与各自天花板

把大模型装进操作系统，目前有三条路，每条都撞到了不同的墙。

路线 A：把 LLM 当内核

代表是 AIOS 这类研究：LLM 视为 CPU、上下文窗口视为内存、工具调用视为系统调用，在应用与模型之间插一层内核做调度与上下文管理。工程价值真实——把上下文管理和调度从各个 agent 框架里抽出来，并发场景下有可观加速。

但那个类比会误导架构。CPU 是确定性、可抢占、状态可完整保存恢复的；LLM 三条全不成立：输出不可复现，上下文即状态，一次推理中途换出等于重算整个 KV。把 LLM 当 CPU，就会推导出「LLM 上下文切换」这种代价极高、本不该存在的机制。

更准确的位置：LLM 是一块高延迟、有损、需要大量随附状态的协处理器。操作系统的任务是虚拟化它，不是让它当大脑。

路线 B：把助手塞进系统

Copilot+ PC 与各类系统级 Agent 入口。天花板被交互模型锁死：用户仍在「开应用—找文件—点按钮」，AI 只是某个环节的加速器。资源抽象、权限模型、状态单位一个都没变，所以它永远只能是插件。

路线 C：把权限收进内核

2025 年之后最有价值的一步。微软的 ACS / MXC 把 Agent 行为切成 8 个拦截点（agent_startup、input、pre_model_call、post_model_call、pre_tool_call、post_tool_call、output、agent_shutdown），用 OPA/Rego 声明式策略做 allow / warn / deny / escalate 四档裁决，用可组合沙箱做强制隔离，并给 Agent 独立身份——它删了文件，日志里记的是 Agent，不是人。

判断是对的：Agent 安全的未来在内核，不在提示词里。但它只解决了一半——管住了「谁能做什么」，没管住「模型看到的东西可不可信」。

三条路线各对了一部分

A 对了「需要一层 AI 运行时」，B 对了「交互必须重做」，C 对了「执行权必须下沉内核」。缺的那块是：信任必须是数据的属性，并随数据在系统内流动。这决定了整个架构的形状。

一个改变判断的新事实

2026 年 7 月，OSWorld（真实计算机环境下的开放式任务基准）上的最好成绩达到 90.2%，而人类基线是 72.36%。两年前 GPT-4o 只有 12.2%。

这个数字的含义比它看起来更重要：「AI 能不能用电脑」这个问题已经基本解决了。那为什么我们还没有 AI 操作系统？因为真正的瓶颈换成了三个——贵、慢、不敢信。OSWorld-Human 的效率研究给出了佐证：成功率最高的 agent 在最严格的效率指标上只有 17.4%，也就是说它做对了，但绕了三四倍的远路、花了三四倍的时间。

所以这份文档的目标不是「让 AI 更强」，而是把已经足够强的能力，变成足够便宜、足够快、足够可信的系统行为。这是操作系统该干的活。

02硬件现实：真正的约束是带宽，不是算力v2 新增

v1 在这里犯了个错：说「NPU 的 TOPS 有限」。这是把 PC 时代的算力思维直接搬过来了。实际情况是——

被普遍误解的一点

端侧大模型推理是内存带宽受限（memory-bandwidth-bound），不是算力受限。生成每一个 token，都要把参与计算的权重从内存搬到计算单元一次。70B 模型 4bit 量化约 35 GB，手机内存带宽按 60 GB/s 算，理论上限就是 1.7 token/s——再怎么堆 TOPS 也没用。一台 40 TOPS 的 AI PC 跑不动 70B，不是因为算力不够，是因为要把 35 GB 搬一遍。

这个修正带来的不是措辞调整，是四个设计结论。

结论一：调度目标从「省算力」变成「省搬运」

既然瓶颈是带宽，推理调度器的核心指标就不该是利用率，而是每生成一个有用 token 需要搬运多少字节。这直接引出三个策略：

  • 驻留感知路由。切换模型意味着重新加载权重，代价是几百毫秒到几秒。如果系统同时轮换使用五个模型，带宽会全部消耗在加载权重上——这叫模型抖动（model thrashing），和内存页抖动是同一个病。对策是硬性约束：同时驻留的模型不超过两个（一个 1–3B 常驻小模型 + 一个按需大模型），路由时优先选择已驻留的模型，即使它的能力略差。
  • 前缀复用。多个 agent 常共享同一段系统提示、同一份文档、同一段对话历史。相同前缀只算一次 prefill，KV 直接复用。这在服务端已是成熟做法（PagedAttention、RadixAttention），但跨应用、跨 agent 的复用只有操作系统能做。
  • 动态精度。同一个模型保留 4bit 与 8bit 两份，难的推理走 8bit，日常走 4bit。精度从「模型属性」变成「调度变量」。

结论二：推理不可抢占，所以必须准入控制

绝大多数 NPU 不支持在一次推理中途换出。这意味着推理调度本质上是非抢占的，和 CPU 的抢占式调度完全不是一回事。一个已经跑了三秒的生成任务，没法为了响应用户的即时请求而中途让路。

可行的做法只有三个：准入控制（估算这个请求要多久，超过交互预算就排队或降级到小模型）、分块解码 + 协作式让出（每生成 N 个 token 检查一次是否有更高优先级的请求，在块边界让出）、预留实时通道（给交互请求保留固定的时间片，后台任务只能填剩余）。

结论三：内存预算决定模型档位

8 GB 内存的手机撑不起稳定的端侧 AI 体验——权重、KV cache、中间激活三者叠加就超了。系统必须有一个显式的模型预算概念：根据可用内存与带宽，判定当前设备能跑哪一档模型，并据此决定路由策略。低端设备不是「体验差一点」，而是根本不该走多步规划，应该直接走确定性宏和单步工具调用。

结论四：长上下文时代，KV cache 比权重更贵

上下文拉到几万 token 时，KV cache 的占用会超过模型权重本身。所以上下文调度在物理上就是内存调度——这两个子系统必须是同一个，不能分给两个人做。

v1 的错误假设修正后架构影响
NPU 算力是瓶颈内存带宽是瓶颈调度目标改为最小化字节搬运
推理可以像线程一样抢占不可抢占，只能块边界让出必须做准入控制，不能靠抢占兜底
模型越多越好，路由挑最强模型切换有重载代价驻留感知路由，限制并发驻留数
上下文管理与内存管理可分开KV cache 是最大内存消费者两者必须合并为一个子系统

03四种同时变稀缺的资源

操作系统的每次演进，都源于出现了一种新的稀缺资源，然后系统围绕它重建抽象：CPU 时间催生进程，内存催生虚拟地址空间，磁盘催生文件系统，网络催生 socket，电量催生移动端生命周期管理。

这一次不是一种资源变稀缺，是四种同时变稀缺，而且互相冲突。

R1

内存带宽

不是算力。生成 token 的每一步都要搬权重，搬不动就是慢，堆核无效。

R2

上下文窗口

新的「内存」，但它是会遗忘的内存：容量有限、访问有损、写错会一直错。

R3

可信上下文

稀缺的不是信息，是能证明来源的信息。混进一段网页文本，整条决策链就被污染。

R4

人的注意力

Agent 越多，请求确认越多。人成了系统里吞吐最低、最容易饱和的组件。

R4 值得单独说。传统操作系统从没把「什么时候可以打断人」当成需要调度的资源——中断来自硬件，数量可控。但 AI 系统里每个后台 agent 都「有话要说」，都想请求确认、汇报进度、报告异常。不加调度，用户会在半小时内被淹没，然后学会全部点「同意」，安全机制就此失效。把注意力当资源调度，是这套设计里最反直觉、也最不可省的一块。

04核心命题：确定化v2 新增

命题 操作系统的历史，就是不断把「慢的、不确定的、需要解释的」变成「快的、确定的、不需要解释的」。缓存把磁盘变成内存，JIT 把解释变成机器码，分支预测把流水线停顿变成无停顿。AI 原生操作系统要做的对应物是：把重复的意图编译成确定性的宏。

为什么这是唯一的长期出路

回到第 1 章那三个瓶颈：贵、慢、不敢信。如果每次都完整地走一遍「理解意图 → 规划 → 执行 → 验证」，这三个数字都不会随时间改善——模型换代能改善一点，但改善的是常数，不是斜率。

而如果同一类意图在第二次、第五次、第二十次执行时越来越便宜，那就是结构性改善。这是操作系统最擅长的事：把重复的工作固化成机制。

三级确定化

级别机制触发条件效果风险
L1 计划缓存复用计划 IR，跳过规划阶段，工具照常执行结构指纹命中省约 70% token，延迟降 30%低：参数仍逐次校验
L2 宏计划编译成带槽位的确定性脚本，参数由轻量解析器填充成功执行 ≥ 5 次且用户确认零 LLM 调用，约 80 ms中：需前置条件检查兜底
L3 触发器条件满足即自动执行，无人参与用户显式授权 + 宏稳定运行 ≥ 20 次约 0 成本，亚秒级高：需「授权预算」上限

宏必须可失效，否则会僵化

确定化最大的风险是：世界变了，宏还在跑。所以每个宏都必须携带前置条件和失效检测：

  • 前置条件：执行前必须验证的世界状态（如「日历该时段仍为空」）。不满足则回退到 L0 概率路径，重新规划。
  • 失效检测：连续 N 次因前置条件失败而回退，宏自动降级并进入重编译队列。
  • 版本绑定：宏绑定工具 schema 的版本。工具接口变了，宏自动失效——这是防止「工具升级后宏静默做错事」的唯一办法。
反直觉的结论

一个成熟的 AI 操作系统，成功标志是它越来越不需要 AI。如果一年后用户 80% 的日常意图仍要靠大模型现场推理，那说明这个系统只学到了皮毛——它把 AI 做成了一个更贵的命令行，而不是一个操作系统。

为什么只有操作系统能做

应用层做不了这件事，有三个原因：应用看不到跨应用的意图重复（你在邮件里归档发票、在文件管理器里归档发票，是同一个意图）；应用无法保证宏的前置条件检查不被绕过（那是内核的活）；应用之间无法共享宏库（每个应用都要从零学一遍）。

确定化本质上是系统级的资源策略，不是应用级的功能。这是这份设计里我认为最站得住的一条。

05六条设计公理

Ⅰ

AI 提议，内核执行

大模型永不进入可信计算基。它可以读、想、说，但任何改变外部世界的动作，必须由内核在能力校验之后代为执行。

Ⅱ

信任是数据的属性，不是进程的属性

一个 agent 进程里既有用户亲口说的指令，也有刚从网页抓来的段落。两者必须区别对待，且标签要随数据流动——污点追踪在 AI 时代的复活。

Ⅲ

一切副作用必须可补偿

隔离挡不住已经发出去的邮件。撤销不是产品功能，是安全机制，必须和权限检查同级。

Ⅳ

确定性外壳，概率性内核

理解、规划、生成往上推，允许不确定；鉴权、执行、记录、回滚往下压，必须确定。系统形状是沙漏，不是直筒。

Ⅴ

降级是一等公民

模型不可用、断网、超预算、电量告急时，系统必须退回传统交互并保持可用。这是最好的架构检验器：如果离了模型开不了机，分层就是假的。

Ⅵ

重复即应确定化

任何被重复执行的意图，都有义务被逐步固化为确定性路径。不确定性是成本，不是特性；能消掉的不确定性必须消掉。

06总体架构

为什么 AI 运行时不能进内核

诱惑很大：上下文管理、推理调度看起来像内存管理和 CPU 调度。但代价不可接受：可信计算基从几万行涨到几百万行外加模型权重，形式化验证彻底失去可能，一次提示注入直达最高权限。

正确做法：AI 运行时是特权但不被信任的用户态服务集。它通过正常的能力申请流程请求内核做事，和第三方 agent 待遇相同，只是能力集合更宽、优先级更高。即使被完全攻破，攻击者拿到的也只是它当时持有的那几张令牌。

可检验的判据

如果明天删掉所有模型文件，系统还能开机、还能打开文件、还能用传统方式完成大部分日常操作——架构是对的。如果开不了机，那它就不是操作系统，是一个包装成操作系统的应用。

07意图编译器与效果类型系统v2 新增

现在所有 agent 的工作方式都是「先做，做错了再修」。这在操作系统层面不可接受——因为有些错误一旦做出去就收不回来。

本章提出一个替代方案：在产生任何副作用之前，用类型系统静态拒绝掉坏计划。这不是新想法（编译原理早就有），但把它用在 agent 计划上，据我所知还没有系统实现。

效果类型：让「发两次」编译不过

给每个工具一个类型签名，其中副作用用线性箭头 ⊸ 标注——意思是这个值只能被消费一次：

// 普通读取：可重复
read_file   : Path → Text
search_mail : Query → List<Mail>

// 线性副作用：只能发生一次
send_mail   : Draft ⊸ Receipt
transfer    : (Account, Money) ⊸ Receipt
delete      : File ⊸ Unit

// 计划本身带效果行
archive_invoices : Effect<{read: File, send: Mail, write: Ledger}> ⇒ Report

线性类型的价值立刻显现：「把同一封邮件发给同一个人两次」在类型层面就是非法的。这类重复副作用是 agent 最常见的灾难性错误之一（重试逻辑写错、循环没退出），而传统做法只能靠运行时去重。

能力可达性检查

计划需要的效果集合，必须是当前能力集合的子集。不是的话，在编译期就失败，而不是执行到第三步才发现没权限。

需要: {read: File, send: Mail, write: Ledger}
持有: {read: File, write: Ledger}
✗ 编译失败：缺少 send:Mail 能力
→ 提示用户授予，或提供不含发送的替代计划

这个检查的工程价值被低估了。现在 agent 最常见的失败模式是「做了 80%，卡在最后一步」，用户看到的是一个半成品状态。编译期检查把这类失败提前到了零成本阶段。

前置 / 后置条件

每个计划携带可执行的世界状态断言：

  • pre: calendar.slot_free(t) ∧ mail.count(unread) < 50
  • post: report.exists() ∧ report.line_count > 0

前置条件在执行前校验，不满足则重新规划；后置条件在执行后校验，不满足则触发补偿。这是确定化宏能够安全存在的基础——宏之所以敢零模型执行，就是因为它带着这些断言。

顺带得到：风险分级

类型系统还能自动算出风险等级，不需要额外配置：

计划涉及的效果风险默认处置
只有 read低直接执行
read + write（本地）中执行后可撤销
含 send / publish（对外）高执行前确认
含 transfer（资金）极高确认 + 冷静期 + 二次验证

注意这里没有任何模型参与判断——风险等级是类型推导出来的，因此不可被提示注入篡改。这是一个很重要的性质。

Agent 的控制组：cgroup 的对应物

每个 agent 属于一个 agent group，拥有五类配额，超出即被内核限流：

  • token 预算：本次任务最多消耗多少推理 token
  • 搬运预算：最多多少字节的权重/KV 搬运（对应带宽这个真实瓶颈）
  • 能力配额：最多同时持有多少张能力令牌
  • 副作用配额：最多能发起多少次写/发送/转账
  • 注意力配额：最多能打断用户几次（见第 14 章）

最后一类是全新的，也是最容易被设计者忽略的——但它是唯一直接约束「系统有多烦人」的机制。

09五个调度器

调度器调度对象优化目标策略要点
① 算力调度线程、页、IO 队列利用率与尾延迟沿用成熟做法，为推理预留实时通道
② 推理调度 新token、KV cache、字节搬运量首 token 延迟、每焦耳 token 数驻留感知路由、前缀复用、准入控制、块边界让出
③ 上下文调度 新上下文窗口（会遗忘的内存）有效信息密度、语义缺页率语义换页、摘要驱逐、按需重取
④ 注意力调度 新人的打断次数与时机「这次打断值得」的比例拥塞控制、合并、分级、静默期
⑤ 信任调度 新能力令牌越权率、爆炸半径最小权限、短租约、逐级升级、负能力

② 推理调度：三个必须同时满足的约束

这是 v2 改动最大的一节。v1 把它当「CPU 调度 + NPU 队列」，错了。真实约束是三条同时成立的：

  1. 带宽受限：换模型 = 重载权重 = 几百毫秒到几秒。所以路由必须驻留感知：优先选已加载的模型，即使能力略差。
  2. 不可抢占：NPU 不支持中途换出。所以必须准入控制：估算耗时，超预算就排队或降级，不能靠抢占兜底。
  3. 前缀可复用：相同前缀只算一次 prefill。这在服务端已成熟（PagedAttention / RadixAttention），但跨应用复用只有 OS 能做。

三条合起来的调度策略：限制同时驻留模型数 ≤ 2；交互请求走预留时间片；后台任务在块边界让出；前缀缓存按 LRU 跨 agent 共享。

③ 上下文调度：语义缺页

上下文窗口是新的内存，但和真内存有个本质区别：缺页是概率的。真 MMU 缺页一定取得到；语义召回可能返回错的，也可能什么都返回不了。

所以上下文调度器必须维护显式的「缺页置信度」并定义三级降级：置信度高 → 直接用；中等 → 补充检索或换表述重试；低 → 停下来问人。把「我不知道」变成可调度的事件，而不是让模型编一个答案。

④ 注意力调度：见第 14 章

这一块单独成章，因为它值得一套完整的控制论设计。

⑤ 信任调度：把安全当配额

权限不是一道静态的门，而是随时间逐步发放、可随时收回的资源。agent 起步只拿「读这三个文件」，随任务推进和用户确认逐步升级，任务结束立刻失效。即使某环节被攻破，攻击者拿到的也是一张快要过期、范围极窄的票。

10上下文与记忆

记忆决定了系统是「每次从零开始」还是「越用越懂你」。它也是最危险的部分——记错的东西会一直错下去，而且越用越自信。

层内容介质生命周期写入规则
L0 工作集当前 prompt 与 KV cacheNPU 显存秒级自动，可随时丢弃
L1 情节最近交互、事件流、任务轨迹本地向量库 + 事件日志天到周自动写入，带完整出处
L2 语义 / 程序提炼的事实、偏好、可复用技能结构化库 + 小模型月到永久需置信度阈值 + 用户可见
L3 冷存档原始记录、加密备份本地磁盘 / 用户自有云永久只追加，不可改

三条不可妥协的规则

无出处不落库。每条记忆必须带 provenance：何时、从哪来、谁说的、当时置信度。无出处的只能待在 L1，不能升级到 L2。

置信度随时间衰减。「用户喜欢靠窗座位」三年前成立不代表今天成立。记忆需要半衰期，过期自动降级，重要决策前重新确认。

记忆必须可审阅、可删除。用户应能像查征信报告一样看到系统记住了什么、依据是什么、用在了哪里。这既是隐私要求，也是纠错机制——模型自己不会发现记错了，只有人能看到。

记忆投毒：这是有实证的攻击

2026 年的研究（《Poison Once, Exploit Forever》）已经证明：恶意内容一旦进入 agent 记忆库，会在之后每次会话被反复「喂」给模型，形成永久驻留的攻击面。这不需要攻破任何加密，只需要让模型「读到」并「记住」。所以记忆写入必须是受控的系统调用，不能是 agent 随手一写。

工程上的四层防御

  1. 写入白名单：只有经过验证的通道（用户直接输入、系统签名的事件）才能写 L2。来自网页、邮件、第三方 API 的内容只能写 L1，且带 untrusted 标签。
  2. 高风险记忆双通道验证：涉及权限、支付、身份的记忆，必须两个独立来源一致才能落库。
  3. 定期记忆体检：扫描无出处、孤立（没有任何引用它的推理链）、与已确认事实矛盾的条目，主动标记待审。
  4. 召回时按信任加权：同等相关度下，可信来源的记忆优先；untrusted 记忆在进入 prompt 时必须显式标注来源。

11现实缓存：给外部世界做缓存一致性v2 新增

Agent 每一轮都要知道世界状态：日历那个时段空不空、这封邮件读没读、文件改没改。每次都去查 API，慢、有限流、还贵。

但直接缓存又不行——世界会变。这就是一个经典的缓存一致性问题，只不过缓存的对象不是内存块，而是现实。

四种状态

借 MESI 协议的结构，但语义要改：

状态含义可以读吗离开条件
E 独占最新刚取回，且确认没有并发修改可以，无需校验本地写 → M；收到外部变更 → I
M 已修改待确认我们本地改了，尚未收到服务端回执可以（read-your-writes）收到回执 → E；冲突 → I
S 共享可能过期曾经正确，但可能有别人改过可以，但高风险操作前需 revalidaterevalidate 成功 → E
I 失效已知过期不可以，必须重取重取 → E

一致性等级由工具声明，不由调用方决定

这是这个设计的核心。不同工具对新鲜度的要求差了几个数量级，统一处理要么太慢要么太危险：

工具类别一致性等级行为
支付、转账、余额强一致每次重读，禁止使用缓存
日历、任务、文件因果一致保证 read-your-writes，写后读必见自己的写
天气、新闻、股价最终一致TTL 10 分钟，过期重取
设备状态（电量、位置）尽力而为本地传感器直读，不进缓存

把一致性等级写进工具清单，意味着应用无法为了性能偷偷降低一致性——这是操作系统该守的底线。

失效的三个来源，按优先级

  1. 推送（最好）：服务端支持变更通知时，实时失效。成本最低、准确度最高。
  2. TTL（次好）：按工具声明的时长过期。
  3. 用前校验（兜底）：高风险操作前强制 revalidate，即使缓存看起来是 E 状态。

冲突处理

M 状态下收到外部变更，就是冲突。此时不允许自动合并——现实世界的冲突（两个人都改了同一场会议时间）往往需要人的判断。系统应触发 yield，把两个版本并列呈现，让人选。

为什么这个抽象值得做

没有它，每个 agent 都要自己实现一套「查—缓存—失效—冲突」逻辑，而且互相不一致。有了它，「世界现在是什么样」变成一个系统服务，agent 只需要声明自己要什么级别的新鲜度。这是把一件每个应用都做错的事，变成一件系统做对一次的事——操作系统的经典价值。

12投机执行与提交验证v2 新增

Agent 的主要延迟不在模型解码，而在等工具返回。一次编译、一次 API 调用、一次文件扫描，动辄几十秒。而这段时间里模型是空闲的。

2026 年的研究（TomasuLLM）已经把这个想法工程化了：把 CPU 的乱序执行搬到 agent 工具调用上，投机预测下一步动作并提前在沙箱里执行，命中时提速 1.27–1.35 倍。

它的三个关键机制值得直接采纳：

  • 乱序发射、顺序提交：可以提前做，但只有验证通过的结果才对主 agent 可见。
  • 预测 ≠ 证据：预测出的 observation 只能让下游推理继续跑，绝不能当作事实提交。
  • 四个验证谓词：动作一致 V_act ∧ 依赖新鲜 V_dep ∧ 观察完整 V_record ∧ 副作用安全 V_effect。

操作系统该补的三件事

但论文自己也承认了代价：每省 1 秒实际耗时，要花 2.1 秒投机算力。在插电的服务器上这是划算的，在靠电池的手机上是灾难。这恰恰是操作系统必须介入的地方。

一、投机预算：把投机当可关闭的调度策略

投机消耗真实的算力和电量，必须计入 agent 的 cgroup。开关条件应该是系统级的：

  • 电量 < 20% 或温度接近阈值 → 关闭投机
  • 用户正在等待（前台交互）→ 开启，因为省的是人的时间
  • 后台批处理 → 关闭，因为没人等，省算力更重要
  • 工具耗时占比 f < 40% → 关闭，因为理论上限 1/(1−f) 太低，回不了本

最后一条是硬门槛。投机只在高延迟工具上划算，在亚秒级调用上纯亏。

二、语义投机：OS 才有的全局视野

论文的投机停留在「预测下一个工具调用」。操作系统能看到更多：

  • 预取上下文：用户说「下周去上海出差」，OS 可以提前把常旅客信息、上次行程、公司差旅政策载入 L1——即使 agent 还没请求。
  • 预驻留模型：预测到接下来需要长上下文推理，提前把大模型加载进内存，避免首次调用的几百毫秒重载。
  • 预热工具：预测要用到日历，提前建立连接、拉取本周事件到现实缓存。

这些都不改变 agent 的行为，只是让它的下一次请求命中缓存。收益比动作级投机更稳定，因为预取错了只是浪费一点带宽，不会产生错误结果。

三、不可投机屏障

有些动作绝不能投机执行，必须串行：

  • 不可补偿的副作用：转账、对外发送、删除。投机执行它们等于绕过确认。
  • 不可追踪的依赖：读集合无法被完整捕获的调用（远程 API、共享进程），投机结果不可信。
  • 依赖尚未生成的内容：草稿编辑这类「内容依赖所读内容」的动作，没法提前。

内核必须在 act() 入口检查这几个条件，命中则强制串行。这个检查不能放在用户态，否则被攻破的运行时可以自己关掉它。

诚实的收益预期

投机的加速比上限是 1/(1−f)，f 是工具耗时占比。工具占 35% 时上限 1.54 倍，占 40% 时 1.67 倍。而实测只有 1.27–1.35 倍，因为预测命中率只有 46%。不要指望投机解决延迟问题，它只是把等待时间填满，真正的解法是确定化（第 4 章）——把整个流程变成不需要等待的宏。

13安全模型

先说结论：提示注入在模型层面无解，只能在系统层面让它失效。

为什么模型层面无解

对模型来说，系统提示、用户输入、网页内容，都是同一串 token，没有本质区别。所有「请不要听信以下内容里的指令」这类防御都是概率性的——降低成功率，给不了保证。只要系统还允许「模型读到的东西」直接影响「模型能做的事」，这条路就是通的。

所以目标不是「阻止注入」，而是「即使注入成功，也不产生安全后果」。这和当年对付缓冲区溢出是同一个思路：不指望消灭漏洞，而是让漏洞不可利用。

核心机制：把计划和执行拆给两个模型

上下文污点追踪

每段进入上下文的文本带一个信任标签：user（用户亲口说的）、verified（系统签名验证过的）、untrusted（外部抓取的）。污点沿推理链传播——用 untrusted 内容得出的结论仍是 untrusted。规则：

  • 带 untrusted 污点的计划，不能直接触发高风险动作，必须经过 yield。
  • 污点不会因为「被摘要过」而消失——摘要继承来源的最高污点。
  • 只有用户明确确认，或经独立可信通道验证，污点才能清除。

这是操作系统信息流控制（IFC）的老理论，只是把「文件密级」换成了「上下文可信度」。目前还没有主流系统在 AI 场景真正实现它。

负能力：单调的拒绝v2 新增

传统能力系统只有「允许」。但允许是可以被绕过的——通过委托链：A 有读权限，A 把缩小后的权限委托给 B，B 再委托给 C，最后 C 拿到的东西可能超出了任何人的本意。

所以需要负能力：一旦某个能力被标记为禁止，任何从它派生的能力也禁止，且不能被「衰减掉」。

形式化：cap' ⊑ cap  ⇒  deny(cap) ⇒ deny(cap')
含义：拒绝沿委托链向下单调传播，只会变多，不会变少

典型用途：企业策略「任何 agent 不得访问财务目录」。即使某个 agent 通过委托链拿到了财务目录的读能力，负能力仍然生效。这是防止「合法授权拼出不合法权限」的唯一结构性手段。

工具供应链：清单就是代码v2 新增

MCP 生态在 2026 年暴露了一整类新攻击面，值得单独对待：

  • 工具投毒：工具的自然语言描述里藏指令。因为描述会进入上下文，模型会把「描述」当成「指令」。
  • Rug Pull：工具通过审核后偷偷改描述或行为（CVE-2026-59822 一类）。
  • Confused Deputy：工具借调用者的权限做调用者无权做的事。

三条对策，全部在系统层实现：

  1. 描述哈希固定：工具描述在首次批准时算哈希并钉住，之后任何变更都使授权失效，需要重新批准。
  2. 描述是数据，不是指令：工具描述进入上下文时必须带 untrusted 标签，并做聚光处理（定界符 / 数据标记）。
  3. 能力显式传递：工具代调用时，必须显式传入一张能力令牌，不能「借用调用者的权限」。

权限模型：能力，而不是身份

  • 不可伪造：令牌由内核签发，用户态无法构造。
  • 可衰减：可以缩小后转授（只读、单文件、十分钟），不能放大。
  • 短租约：默认 10 分钟过期，长期任务需续租，续租时重新评估风险。
  • 可撤销：一键收回，进行中的动作立即中止并触发补偿。
  • 可归因：每次使用记录在行动账本上，能回答「这个文件是谁在何时为何读的」。

14注意力拥塞控制v2 新增

这是我认为最被低估的一块，也是唯一能直接决定「用户会不会关掉这个系统」的机制。

把打断看成丢包

网络拥塞控制的本质是：发送方不知道链路容量，只能通过「丢包」这个信号推断，然后调整速率。用户注意力是完全一样的结构——系统不知道用户现在忙不忙，只能通过「忽略 / 拒绝」这个信号推断。

所以直接借 TCP 的 AIMD：

  • 加性增（Additive Increase）：用户持续响应时，允许的打断频率线性增加。
  • 乘性减（Multiplicative Decrease）：被拒绝或忽略时，频率折半。
  • 慢启动：新 agent 从很低配额起步，表现好才加速。这防止一个新装的 agent 立刻开始轰炸。
  • RTT 类比：从请求到用户响应的延迟。响应很慢说明用户在忙，应主动降速——不必等到被拒绝。

公平性：max-min

多个 agent 竞争同一个人的注意力，用 max-min 公平分配：先保证每个 agent 拿到最低配额，剩余额度再按需求分配。这样不会出现「一个话多的 agent 饿死其他所有 agent」。

中断定价

更激进一点：给每次打断标价，agent 必须从自己的注意力配额里「付钱」。这会自然产生正确的行为：

  • agent 会主动合并多个确认请求（省钱）。
  • agent 会倾向于选择「默认安全动作 + 事后告知」而不是「事前询问」（更省钱）。
  • 只有真正重要的事才值得花配额——这个判断由 agent 自己做，而不是由用户配置。

分级：什么才配立即打断

级别条件行为

如果注意力配额是静态配置，用户要么配得太松被淹没，要么配得太紧错过重要确认。做成自适应回路之后，系统会自己学会什么时候该闭嘴——而这恰恰是所有人对 AI 助手最朴素的期待。

15动作与事务

隔离挡不住已经发出去的邮件。这是 AI 系统和传统系统的根本差异：它的错误会离开计算机。

所以每个 act() 都必须在事务里执行，附带三类元数据：

  • 幂等键：重试不会重复下单。在网络不稳、agent 反复重试时是救命的。
  • 补偿动作：后续步骤失败时怎么撤回这一步。发邮件没有真正的补偿，那就必须在发送前设更高的确认门槛——不可补偿的动作，必须用更严的前置约束来换。
  • 前置条件：执行前世界必须处于什么状态。不满足则整个事务不启动，而不是做到一半才发现。

三档可补偿性

档位例子策略
可完全补偿本地文件操作、草稿允许后台 agent 自主执行，随时可撤
可部分补偿撤销 API 存在但有时间窗（发送后 30 秒内可撤回）必须走确认，且提示时间窗
不可补偿对外通信、支付、物理动作禁止后台自主执行，必须前台确认 + 冷静期

冷静期：给不可逆动作加一个倒计时

借鉴银行转账的延迟到账。对不可补偿动作，系统不立即提交，而是进入 pending 状态，显示倒计时（比如 10 秒），期间可一键取消。这不是技术限制，是利用人的后悔反射——大部分误操作在几秒内就会被自己发现。

可重放：给概率系统装调试器

传统系统出问题，复现一遍就行。AI 系统不行——同样的输入，模型可能给出不同结果。所以系统层记录「决策轨迹」：每个决策点的输入摘要、模型版本与参数、输出、工具返回、当时的能力集合。有了它才能时间旅行调试：回到第 7 步，看当时模型看到了什么、为什么选了那个工具。

这份轨迹同时是合规审计、责任归属、模型迭代回归测试的基础设施。没有它，系统在真实环境里无法运维。

「无进展」怎么检测

这是最难的一类，也是最容易被用户感知的——agent 转了十分钟，什么也没做成。检测思路是维护一个任务状态指纹：把当前计划进度、已确认的事实、已完成的副作用做成哈希。如果连续 N 轮指纹不变，判定为无进展。

难点在于「看起来有进展但实际没有」：agent 在反复读同一个文件的不同片段，指纹一直在变，但任务没有推进。所以还需要一个语义层的判据——距离目标的后置条件还有多远。这个判断本身需要模型，但它只在看门狗触发时才调用，成本可以接受。

意图漂移：一个被忽略的问题

用户说「帮我订个会议室」，agent 开始执行，中途用户说「算了，改成线上吧」。传统做法是中止重来，但前面已经查过参会人空闲时间——这部分工作不该丢。

所以意图需要版本化：intent@v1 → intent@v2，系统计算 diff，判断哪些已完成步骤仍然有效，只重做受影响的部分。这和软件构建系统的增量编译是同一个思路。

17多 Agent 并发与冲突v2 新增

真实使用中，用户会同时有多个意图在跑：后台整理文件、前台查资料、定时任务在归档邮件。它们可能碰同一个文件、同一场会议。

隔离：每个 agent 一份 overlay

沿用投机执行那套 COW 沙箱：每个 agent 从已提交状态 fork 一份写时复制快照，写入只落在 overlay 里。提交时才合并到主状态。这样 agent 之间的中间状态互不可见，也不需要复杂的锁。

共享：黑板，而不是消息传递

Agent 之间需要共享知识（「这个供应商的账期是 60 天」），但直接互相发消息会导致 N² 的连接数。所以用黑板：一个只追加的结构化事实库，每条事实带出处和信任标签。Agent 往黑板写，也从黑板读。

黑板的关键约束：只追加，不修改。要推翻一条事实，就追加一条新的并标注它取代了哪条。这样任何时刻都能回溯「当时为什么这么判断」。

冲突：乐观并发 + 提交时校验

不用锁——agent 会长时间持有锁（一个任务可能跑十分钟），锁会导致大面积阻塞。改用数据库那套乐观并发：

  • 每个 agent 记录自己读过哪些对象、什么版本（读集）
  • 提交时检查读集是否仍是最新（写集是否与他人冲突）
  • 冲突则整个事务回滚，agent 重新读取后重试

这套机制在数据库里已经被验证了几十年，直接搬过来即可。唯一的新问题是重试可能再次冲突，需要指数退避 + 上限，超限则升级给人裁决。

死锁：资源全局排序

两个 agent 互相等待对方持有的能力（A 等 B 释放文件锁，B 等 A 释放日历权限）。传统解法是资源全局排序——所有 agent 必须按同一顺序申请资源。这个约束对 agent 来说是可以接受的，因为它们的资源需求是声明式的（第 7 章的效果行），编译期就能排序。

18跨设备分布式能力v2 新增

这个系统不会只活在一台设备上。手机、PC、眼镜、车机、机器人，用户把它们当成一个整体。

能力可以跨设备委托

手机的摄像头是一个能力，可以委托给眼镜上的 agent 使用 60 秒、只读、单次。这比「共享账号」精确得多，也比「投屏」安全得多。

跨设备委托必须带设备证明（attestation）：接收方要能证明自己运行的是未被篡改的系统。没有这个，委托就等于把权限发给了一个未知设备。

一致性：版本向量

现实缓存跨设备时需要同步。用版本向量而不是时间戳——设备的时钟不可信，而版本向量能正确表达「A 看到过 B 的第 3 版，但没看到第 4 版」。

分区：离线时必须诚实降级

设备断连时，最危险的行为是「以为自己在控制另一台设备」。所以跨设备能力必须有租约：连接断开超过租约时长，能力自动失效，本地 agent 必须停下来而不是继续执行。

这条看起来是技术细节，实际上是安全底线。一个以为自己在控制机器人的 agent，如果实际已经失去连接，它的每一条指令都在制造现实世界的错误。

19交互与生态

意图栏取代启动器

主入口不再是图标网格，而是一个输入框——但语义和搜索框完全不同：搜索框返回链接，意图栏返回已完成的结果或正在进行的任务。「把上个月的发票整理成报销单」应该直接产出一个填好的表单，而不是十个可能相关的文件。

关键设计是渐进披露：第一屏只给结论和最关键的一个操作；想深究时展开证据（依据了哪些文件、哪几条记忆）；再深一层是完整执行轨迹。绝大多数时候用户停在第一层，但必须随时能下钻——这是信任的来源。

生成式界面必须被约束

让模型直接生成 UI 很诱人，但会带来三个问题：不可测试、不可无障碍访问、不可审计。Loom 的做法是约束解码到组件词汇表：系统提供一套经过设计、测试、带无障碍标注的组件，模型只能输出「用哪些组件、什么内容、什么布局」的声明式描述，由系统渲染。

这样既保留「界面随任务而变」的灵活性，又保证每个像素都来自可信代码。一句话：模型决定说什么，系统决定怎么画。

环境感知要有可见的开关

三条约束：默认全部在端侧处理，原始数据不出设备；任何时候都有物理可见的指示（不是藏在设置里的小圆点）；一键可关，关闭后系统明确降级而不是偷偷继续。

兼容：不要要求别人重写

历史上所有新操作系统的死因几乎相同：没有应用。Loom 的答案是反向适配：

  • 自动化桥接：通过无障碍树、UI 自动化接口、脚本接口，把已有应用的界面元素暴露成系统工具。老应用不改一行代码就获得被 agent 调用的能力。
  • 渐进升级：应用可以选择提供「语义化动作」（推荐），系统就不必猜界面；不提供也能用，只是可靠性低。
  • 工具即驱动：把「一个应用能做什么」定义成和设备驱动类似的声明式清单，系统统一编排、鉴权、记账。

这条路不优雅，可靠性也不如原生集成，但它是唯一能在第一天就有生态的路。

20内核实现路径v2 新增

第 23 章会说明为什么不能从零写内核。这一章说明如果真的要做，该怎么做——核心原则是不自研已经存在的东西。

不自研能力硬件，骑 CHERI

能力系统最难的从来不是软件，是硬件。而 CHERI 已经把这部分做完了：带边界、权限、类型和有效位的能力指针，Arm 的 Morello 是首个工业级实现，CheriBSD 已经在上面跑起来了。实测能挡住 70% 以上的内存类漏洞。

所以内核的能力模型应该直接建立在 CHERI 之上，而不是自己发明一套软件模拟。软件模拟的能力检查每次都要查表，硬件能力检查是免费的——这个差距在系统调用密集的路径上是决定性的。

不自研微内核，从 seL4 出发

seL4 是世界上唯一经过代码级形式化验证的微内核，本身就是能力制的。它的 IPC 性能在微内核里属于第一梯队。从它出发，意味着可信计算基的正确性已经有了数学证明，你只需要证明自己加的那部分。

需要新增到内核的东西很少：agent 对象的生命周期、cgroup 式的五类配额、负能力的传播规则。这三样都要做形式化验证，因为它们直接承载安全属性。

用户态用 Rust

AI 运行时、语义服务、现实缓存这些用户态组件，用 Rust 写。不是因为性能，是因为内存安全对这类长期运行、处理不可信输入的服务是刚需。而且 Rust 的类型系统天然适合实现第 7 章的效果类型检查。

关键路径的验证范围

组件验证强度理由
能力撤销形式化证明撤销不彻底等于没有撤销
负能力传播形式化证明单调性是安全属性的核心

21尚未解决的问题

只讲优点的架构文档没有价值。以下是设计里没有真正解决的问题。

1. 间接提示注入——语义层仍然未解

双模型分离能切断「读到的内容 → 直接执行」，切不断「读到的内容 → 影响计划 → 计划本身看起来完全合理」。攻击者不要求转账，只让 agent「顺便转发给财务」，这看起来毫无问题。类型检查也拦不住——它在类型上完全合法。

这类语义层操纵目前只能靠概率性检测和人工确认。这是整个领域未来三到五年最重要的开放问题。

2. 确定化会不会让系统变僵

第 4 章的宏编译是核心创新，但它有个内在张力：宏越多，系统越快，也越难适应变化。如果用户的工作模式变了，一堆宏会持续失效、回退、重编译，反而更慢。

目前只有「连续失败即降级」这一条粗糙的规则。真正需要的是宏的生态位管理——知道哪些宏该保留、哪些该淘汰、哪些该合并。这是个开放问题。

3. 长任务卡住而不报错

第 16 章给了检测思路（状态指纹 + 语义距离），但「语义距离」本身要靠模型判断，而模型可能判断错。一个误判会把正在正常推进的长任务杀掉。

4. 级联路由的准确率上限

小模型处理大部分、难的给大模型，是控成本的唯一现实方案。但「难不难」的判断本身靠分类器，它会犯错，且错误方向不对称：简单问题误判为难的，只是慢一点；难问题误判为简单的，就是错误执行。

5. 评估体系缺失

OSWorld 到 90.2% 了，但它测的是「能不能完成任务」，不测「成本多少、打扰几次、撤销几次」。而这些恰恰是操作系统的核心指标。目前没有公认的 OS 级 benchmark，需要真实的长周期用户数据。

6. 常驻感知的功耗

「随时待命」和「一天一充」直接冲突。可行方向是事件驱动而非轮询：绝大多数时间 NPU 休眠，由廉价传感器或规则引擎触发唤醒。但「什么事件值得唤醒」又是一个准确率问题。

7. 用户的信任校准

用户会走向两个极端：过度信任（不看就点同意）或过度怀疑（每次都拒绝）。第 14 章的注意力拥塞控制能减少打扰，但不能保证每次打扰都问在关键处。这更像产品设计问题，却决定了安全机制的实际有效性。

8. 标准化的先有鸡还是先有蛋

如果每家公司都定义自己的工具描述格式和能力模型，最后是一堆互不兼容的孤岛。这一层需要标准化，但标准化通常发生在市场格局确定之后。

P2 内核30–60 月基于 seL4 + CHERI 构建能力原生内核不追求全功能，只做能力与隔离TCB 能否压到可验证的规模

MVP：一个垂直切片，而不是一个平台

第一版不要做「通用助手」，要做一条端到端的窄流程：邮件 + 日历 + 本地文件。用户说「下周去上海出差，帮我把行程排一下」，需要完整走通：

理解意图 → 检索历史偏好（记忆）→ 读日历找空档（能力申请）
→ 查航班（网络工具）→ 生成行程（生成式界面）→ 用户确认
→ 写日历（事务）→ 可撤销 → 第 5 次后编译为宏

这条流程覆盖了全部核心机制：意图、记忆、能力、事务、生成式 UI、撤销、双模型分离、确定化。它跑通了，架构就成立；跑不通，问题会立刻暴露在最贵的地方之前。

一个建议的验证顺序

不要先做「能力」，先做「约束」。因为能力会随着模型换代自动变强，而约束不会——它只能被设计出来。所以 P0 阶段最该验证的三件事，按优先级：

  1. 确定化率能不能真的爬上去（如果爬不上去，整个第 4 章的核心命题就错了）
  2. 误中断率能不能压到 5% 以下（如果压不下去，用户会关掉一切确认）
  3. 类型检查能拦掉多少坏计划（如果拦不住，静态安全就是空话）

24战略定位

最后一个判断，可能比前面所有技术设计都重要。

PC 和手机上有 Windows、Android、iOS，它们有二十年积累的应用生态、驱动生态、开发者习惯。AI 原生 OS 在这两个战场上没有胜算——不是因为技术不行，是因为迁移成本由用户承担，而收益是渐进的。

真正的机会在没有存量生态的新形态设备：

  • 具身智能 / 机器人：交互天然是「说目标」而非「点按钮」。没有历史应用要兼容，感知—决策—执行的闭环本来就是 OS 该管的事。
  • 智能座舱：驾驶场景下用户不能看屏幕、不能点按，意图式交互是唯一合理选择，而不是可选项。
  • AI 眼镜 / 可穿戴：屏幕极小，UI 必须由系统按需生成，固定界面范式根本不成立。
  • 工业与专用终端：任务高度结构化，可靠性要求高，正好是「可审计 + 可回滚」价值最大的地方。

这些场景有个共同点：它们不需要说服用户放弃现有习惯，因为它们本来就是新的。在这里把架构跑通、把可靠性磨出来，再回头打通用计算，胜率完全不同。

一句话总结

这个操作系统的竞争力不在于「模型有多聪明」——那是别人的战场。它在于两件事：当模型犯错、被欺骗、或干脆不可用时，系统还能保证什么；以及同一个意图重复一百次之后，它是否变得又快又便宜又安全。前者是操作系统的老承诺，后者是这个时代的新承诺。
